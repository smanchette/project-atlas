# Project Atlas Metadata Bridge 0.57.16

Version 0.57.16 is a narrow successor to 0.57.15 in the same Metadata Bridge plugin family. It preserves the complete Performance Local V5 renderer, private one-page metadata transport, JavaScript behavior, stylesheet, template, governed business identity, WordPress-native estimate-delivery contract, sticky geometry, interface typography, and private administration surface.

The preserved private WordPress-admin settings surface manages the existing `_project_atlas_estimate_form_delivery_v1` option. The surface is available only when WordPress reports `local` or `staging`, is registered under Settings for users with `manage_options`, accepts mutations only through an authenticated POST with an exact WordPress nonce, and rejects unknown fields. It does not add a public configuration route, another customer-facing form, another plugin, SMTP, a provider SDK, a database table, or customer-submission storage.

Configuration replacement remains disabled-first. The server constructs the existing schema-1 option, Website and form identities, governed field-definition hash, and optional Email-field binding; callers cannot submit arbitrary identities, hashes, duration values, or field structures. The exact optional sixth field is `Email`, key `email`, input type `email`, order 6, optional, maximum length 254, with the existing `email_address` rule. Reply-To can be enabled only for that exact governed field and is emitted only when a submitted value passes strict email validation.

The same private settings page includes one narrowly bounded Page 8 metadata action for environments where browser-script execution is unavailable. The action is rendered only when the current valid `composition:41:v10` payload has either the exact five governed fields or the exact six-field target and the complete six-field private configuration is valid, disabled, and binds enabled Reply-To to the governed Email field. Its POST allowlist accepts only the normal action, command, nonce, and a server-rendered 64-character expected-prior SHA-256. The server appends the exact governed Email field only when absent, constructs the existing page-payload request envelope and UUID, requires the existing private route permission callback, and accepts only an exact HTTP 200 `APPLIED` or `UNCHANGED` response with the expected route, version, page/source identities, hashes, request identity, and metadata-valid marker. Exact metadata and disabled-configuration readback must both remain unchanged after the callback. Existing compare-and-swap and rollback behavior remains authoritative, including write-free repeated execution against the exact six-field target.

When the configured recipient is also the pre-existing governed public contact, the private-value guard continues to exempt only exact byte-preserved `website.contact_email` and `footer.contact_email` values. Version 0.57.16 additionally permits the same recipient inside `body` of the single `final_conversion` section only when the prior and candidate payloads each contain exactly one such section at the same list position and both complete section records are byte-identical. That body is removed only from the in-memory recipient scan. No stored or submitted payload byte is rewritten. A moved, missing, duplicated, or changed final-conversion section receives no exemption; recipient occurrences in any other field remain prohibited. The configured From address is scanned against the complete payload before any recipient-only exemptions and remains prohibited everywhere. No raw payload editor, upload, public route, media action, or core Page 8 field write is added; the interface renders only hashes and redacted state.

The recipient and From-address inputs are always blank on render. Saved private addresses are never echoed in HTML, URLs, public REST output, public JavaScript, or public form output. The settings page displays only redacted configured/enabled/schema/binding/domain/mode state. Enable and disable are separate exact POST commands; enable succeeds only after the current page payload has the exact configured form-field definition.

Every option write retains the prior exact value in request memory, reads the stored option back with strict equality, and restores the prior value when verification fails. No backup option, transient, diagnostics endpoint, or arbitrary option editor is created. Disabling changes only the `enabled` member and retains the validated configuration. A separate authenticated command can remove only a schema-valid disabled configuration and verifies exact option absence, allowing a workflow that freshly proved an unconfigured baseline to restore that exact absence. A workflow that finds an existing configuration must fail closed rather than replace an unknown prior value without a separately authorized rollback mechanism.

From-address validation continues to accept the exact WordPress home hostname. On staging only, it additionally accepts the exact canonical Website domain derived from the trusted canonical Website URL. It does not use suffix matching and does not admit unrelated domains or subdomains. Canonical-domain relaxation is not available in local, development, or production environments.

The private page-payload route remains `GET`, `POST`, and `DELETE /wp-json/project-atlas/v4/performance-local-v5/page-payload/(?P<post_id>\d+)`. The public submission route remains `POST /wp-json/project-atlas/v4/performance-local-v5/estimate`, with its same-origin proof, short-lived signed token, strict field allowlist, honeypot, rate limiting, idempotency, pending lease, generic responses, and one request-scoped `wp_mail()` call.

The existing V5 renderer remains fail-closed outside `local` and `staging`. This package does not seed or enable delivery, store customer submissions, expose private delivery configuration, change Page 8 content or media, or authorize production installation, publication, or deployment.
